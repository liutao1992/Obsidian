# 七、核心业务表设计

---

# users（用户表）

```sql id="r1k0h4"
CREATE TABLE users (
    id BIGSERIAL PRIMARY KEY,
    username VARCHAR(64),
    email VARCHAR(128),
    phone VARCHAR(32),
    created_at TIMESTAMP
);
```

---

# products（商品表）

```sql id="8z8i97"
CREATE TABLE products (
    id BIGSERIAL PRIMARY KEY,
    name VARCHAR(128),
    category_id BIGINT,
    price NUMERIC(10,2),
    stock INT,
    created_at TIMESTAMP
);
```

---

# orders（订单表）

```sql id="5ivp6p"
CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT,
    status SMALLINT,
    total_amount NUMERIC(10,2),
    created_at TIMESTAMP
);
```

---

# order_items（订单详情）

```sql id="mb4q2u"
CREATE TABLE order_items (
    id BIGSERIAL PRIMARY KEY,
    order_id BIGINT,
    product_id BIGINT,
    quantity INT,
    price NUMERIC(10,2)
);
```

---

# payments（支付流水）

```sql id="dq2v8r"
CREATE TABLE payments (
    id BIGSERIAL PRIMARY KEY,
    order_id BIGINT,
    pay_status SMALLINT,
    pay_amount NUMERIC(10,2),
    created_at TIMESTAMP
);
```

---

# user_events（核心日志大表）

这是整个实验最关键的表。

```sql id="n1r1d0"
CREATE TABLE user_events (
    id BIGSERIAL PRIMARY KEY,
    user_id BIGINT,
    event_type VARCHAR(64),
    device VARCHAR(64),
    ip VARCHAR(64),
    payload JSONB,
    created_at TIMESTAMP
);
```

这个表会产生：

* 高频 INSERT
* 大量 WAL
* 大量索引更新
* Vacuum 压力
* 时间范围查询
* 热点更新

这就是生产环境中的典型问题。

# 八、数据规模（非常关键）

很多人实验失败：

因为：

```text id="5j2xmk"
只有几千行数据
```

这种规模：

根本无法观察：

* planner
* vacuum
* checkpoint
* WAL
* IO
* bloat

---

# 推荐数据规模

## 初级阶段

```text id="wy0tw2"
users           10万
products        10万
orders          100万
order_items     300万
user_events     1000万
```

数据库体积：

```text id="x3c4sm"
10GB ~ 30GB
```

必须：

# 数据量大于内存

否则：

所有数据都在 page cache 中。

你永远看不到：

* Disk IO
* Buffer Miss
* Checkpoint Flush

---

# 九、一定要模拟“脏数据”

真实生产里：

数据永远不是“干净”的。

你必须模拟：

* 数据倾斜
* 热点用户
* 热点商品
* NULL
* JSONB
* 长文本
* 高频 UPDATE

否则：

很多性能问题根本不会出现。

# 十、PostgreSQL 推荐配置（2C2G）

## postgresql.conf

```conf id="7mz74u"
# =========================
# MEMORY
# =========================

shared_buffers = 512MB

work_mem = 4MB

maintenance_work_mem = 128MB

effective_cache_size = 1GB

# =========================
# WAL
# =========================

wal_buffers = 16MB

max_wal_size = 2GB

min_wal_size = 512MB

checkpoint_timeout = 5min

checkpoint_completion_target = 0.8

# =========================
# CONNECTION
# =========================

max_connections = 100

# =========================
# AUTOVACUUM
# =========================

autovacuum = on

autovacuum_max_workers = 2

autovacuum_naptime = 10s

# =========================
# LOG
# =========================

logging_collector = on

log_checkpoints = on

log_lock_waits = on

log_temp_files = 0

# =========================
# EXTENSION
# =========================

shared_preload_libraries = 'pg_stat_statements'

pg_stat_statements.max = 10000

pg_stat_statements.track = all
```

# 十一、必须学习的核心实验

---

# 实验1：索引失效

SQL：

```sql id="4qucwa"
SELECT *
FROM users
WHERE LOWER(username) = 'tom';
```

学习：

* Seq Scan
* Index Scan
* Bitmap Heap Scan

理解：

为什么函数会导致索引失效。

---

# 实验2：回表问题

学习：

* covering index
* heap fetch

理解：

为什么：

```text id="v1j4ys"
“有索引”
不代表一定快
```

---

# 实验3：大 OFFSET 分页

SQL：

```sql id="1z2mfd"
SELECT *
FROM orders
ORDER BY id
LIMIT 20 OFFSET 1000000;
```

现象：

```text id="g4g4ps"
execution time 暴涨
```

学习：

* Keyset Pagination
* 深分页问题

---

# 实验4：Checkpoint 抖动（核心）

持续 INSERT：

```sql id="9jj19v"
INSERT INTO user_events ...
```

观察：

```text id="jtvf3z"
TPS 周期性下降
IO 突然暴涨
```

学习：

* WAL
* Checkpoint
* Dirty Page Flush

重点参数：

```conf id="i8mzt9"
checkpoint_timeout
max_wal_size
checkpoint_completion_target
```

---

# 实验5：autovacuum 跟不上

持续 UPDATE：

```sql id="l8s4gk"

SET payload = ...
```

观察：

```text id="o9fr48"

index bloat
```

学习：

* MVCC
* Vacuum
* Freeze

---

# 实验6：WAL 暴涨

高频 INSERT：


观察：

```text id="3xsyq1"

```

学习：

* wal_buffers

# 十三、真正贴近生产的关键

---

# 1. 持续压测

不是：

```text id="2y2t3o"
跑一次 SQL
```

而是：

```text id="xtuk4r"
持续 2 小时
持续写入
持续更新
```

因为：

* autovacuum
* checkpoint
* WAL

都需要时间积累。

---

# 2. 数据必须足够大

至少：

```text id="8zpt0h"
几十 GB
```

否则：

```text id="y93j8p"
page cache 全缓存
```

根本无法学习 IO。

---

# 3. 必须限制资源

你的：

```text id="u5j0fu"
2C2G
```

其实非常适合学习。

因为：

你会真正理解：

```text id="7h2n7m"
数据库性能
本质是资源竞争
```

而不是：

```text id="3j5j3r"
SQL 不快 → 加机器
```
